# Engineering skills (S1-S19)

Reference for the akzo-master-sdd agent: read when a step names a skill (S<n>); apply it in the phase it names. The repository's own conventions win where they differ.

## Agent Maintenance
Read only for internal agent corrections or upgrades, before application routing.
- **Maintenance boundary (before application routing):** identify the active workspace, Git root, and repository role from files and remote evidence. A source checkout contains `VERSION`, `copilot/agents/akzo-master-sdd.agent.md`, `copilot/modules/investigate/scripts/akzo.ps1`, and `scripts/install.ps1`; installed copies and applications containing copied agent files are not proof. Verify repository identity and source layout, not the folder name alone. Edit only the verified checkout or an explicitly supplied, verified source path. Never implement agent-runtime improvements inside a target application repository or use application tests as agent validation.
- **Missing agent source:** report the missing repository once and stop modifying code. Do not edit application source, tests, guidance, installed copies, or memory as a substitute. No repeated discovery or questions; resume only with new source-location evidence.
- **Routing:** do not invoke `task`, `pick`, `issue`, or application profiles. No PBI ID is required unless the developer explicitly requests a genuine PBI-tracked workflow. Read only relevant agent source and its existing checks; no application pipeline, spec, or plan.
- **Fast execution:** identify affected files before editing; reuse current repository indexes and prior verified findings. Batch independent targeted searches/reads and coherent edits; do not rescan the whole repository, reread unchanged evidence or reload skills/profiles. Use targeted analysis -> targeted edits -> focused tests -> diff inspection. Recheck only evidence invalidated by source, scope, toolset or dependency changes. Reuse resolved same-task decisions; retain required IDE/security/install prompts and approval for changed scope. Continue after passing focused checks; do not pause for routine permission or repeat progress/completion messages.
- **Unintended application edits:** inspect the named file's complete diff and directly coupled changes read-only. Report whether a revert is warranted and why; dirty diffs alone do not prove authorship. Never discard unrelated user changes or revert a coupled test in isolation; revert only confirmed agent-owned edits when authorized.
- **Validation:** use the checkout's actual components and dependencies. Small changes use relevant focused tests, `scripts/test.ps1 -StaticOnly` and diff inspection. Analyzer/workflow changes add component regressions, semantic cold/incremental equivalence and affected integration checks; build only changed agent components. Broader regression requires demonstrated impact or release policy, not every edit. Release packaging requires the complete regression, installer/GUI checks (live UI limitations explicit), manifest validation and package integrity; incomplete validation is never a full release PASS. Application-specific helper, Sonar, business-rule, and completion steps below apply only to application work; applicable security controls remain required. If taskless security tools reject agent source, report the exact limitation without inventing a PBI or switching repositories.
- **Retrieval and measurement:** C# `arch -Queries "HandlerName;ValidatorName;ServiceName"` shares one semantic refresh across up to eight relevant queries; do not split it into repeated helper calls. TypeScript uses `-Query`. For analyzer source-only iterations with a successful current restore and unchanged dependencies/SDK/NuGet configuration, use `scripts/build-analyzer.ps1 -NoRestore`; otherwise restore normally. Readiness/GraphQL content hashes and semantic dependency invalidation remain authoritative; never trade correctness for timestamp-only reuse. Reuse unchanged Sonar evidence only for the same scope/source revision; rerun after relevant edits. Record discovery, architecture, edit, test and total elapsed times, cache hit/miss counts and actual tool/helper invocations in task evidence. Count duplicate searches; report model calls/tokens only when host telemetry exposes them. Compare equivalent cold/warm runs; keep process-count reductions distinct from host-tool or model-call reductions.
- **Isolation and report:** conversation-specific decisions, corrections, approvals, and performance observations stay in conversation or existing task evidence, never repository memory. Finish once with source identity, version before -> after, changes, actual checks, preserved application work, and unverified items. Do not repeat completion summaries or claim 10/10 without measured evidence. Instruction changes are not deterministic edit-blocking enforcement; source upgrades are not installed releases.

## S. Engineering skills (apply in the phase named; the repository's own conventions win where they differ)
- **S1 Requirement sharpening (Intake, Spec):** restate the goal, actor, and success signal in one line each; list hidden assumptions and check each against the PBI or code. A capability that spans several independently testable behaviors is split into numbered requirements before ACs are written. Non-goals are written down.
- **S2 Source-driven decisions (every code change):** identify the active solution and affected projects, refresh Roslyn evidence where applicable, and source-verify the closest implementation's relevant execution chain. Detect exact framework/package versions from manifests and lock files; choose APIs that exist there. Consult current repository evidence, memory, and prior approved decisions before asking a short free-text question. Reuse an existing symbol before creating a new one; no speculative contracts, GraphQL fields, Dataverse attributes, or generated edits. Direct fixes use working context, never new plans.
  - **Internal execution map (not a planning document):** keep a compact source-verified chain for the affected operation: entry point -> command/query -> handler -> validator -> service/interface -> repository/data access -> entity/contract mapping -> DI -> tests, including only roles this architecture actually uses. Each relied-on link names the real symbol and `path:line`; inspect implementers and consumers when signatures or behavior change. PBI work records this evidence in its existing spec/plan; fixes keep it in working context and report only the decisive references. Do not create a plan, decision map, or architecture document for a direct fix.
  - **No speculative implementation:** verify existing symbols, contracts, DTO fields, GraphQL operations and generated signatures, Dataverse entity/attribute logical names, option values, mappings, and registrations before relying on them. Never invent them from a skill example or inferred pattern. Proposed new classes require a demonstrated gap, the closest sibling, correct layer, real consumers, and a reason existing code cannot be reused. Never hand-edit generated output; change its verified source and use the repository's generator.
- **S3 Architecture and design review (Spec, Plan, Review):** follow the dependency direction the repository already uses (for layered or clean architectures: domain <- application <- infrastructure/entry points/UI; no infrastructure types in the domain); one handler per command or query where the repo uses CQRS, commands change state and queries do not; input rules in validators, orchestration in handlers or services, business rules in the domain or services, as the siblings place them. Flag god classes, leaked infrastructure types, static state, service locator use, and duplicated business rules. Add a pattern (factory, strategy, decorator, result type) only when a sibling already uses it. Prefer explicit, obvious code over clever abstractions.
- **S4 Interface and contract design (Spec, Plan):** for every changed endpoint, function, contract operation, model, or UI service write the before/after contract, nullability, error shape, and who consumes it. Prefer additive changes; a breaking change needs a migration note and is a Stop condition. Inputs are validated at the trust boundary; outputs never expose internal entities.
- **S5 Stack profile: .NET / C# (when `architecture.stack` lists dotnet):** nullable reference types respected (no `!` to silence warnings without a proven invariant; guard clauses for public inputs); async all the way with `...Async` names, `CancellationToken` passed through and last, no `async void`, no `.Result`/`.Wait()`, `ConfigureAwait` only where the repo uses it; options pattern for configuration; immutable records for DTOs when siblings use them; structured logging templates (no string interpolation in log calls, no secrets or personal data); exceptions mapped the way siblings map them; data queries projected and filtered on the server, no-tracking reads where the repo does, no N+1 loops. Other stacks: derive the equivalent rules from the repo's code, linters, and guidance.
  - **Validation discovery and planning:** detect FluentValidation from the affected project's resolved packages, Roslyn `AbstractValidator<T>` implementations and real execution path, not a repository name or an unrelated sibling project. Reuse the closest validators, shared rules and child validators; record their exact symbols, application-layer locations, registrations/lifetimes and pipeline or explicit invocation. In projects already using FluentValidation, new request, command and side-effect-free business-rule validation uses that pattern: `RuleFor`, `Must`, `MustAsync`, `When` and dependent rules as appropriate. External-service/database checks use asynchronous rules and awaited `ValidateAsync` with cancellation through the existing pipeline; verify the installed version and that the pipeline supports async rules. Validators execute before the business operation. Do not duplicate validation inside Functions, Controllers or Handlers; preserve domain invariants, authorization/security checks and state-changing orchestration in their existing owners.
  - **Validation contracts and tests:** preserve the existing error-response contract: property names, messages, error codes, HTTP status, GraphQL error shape and middleware/exception translation. Plan valid, invalid, null, empty and boundary-value unit cases, async failure/cancellation cases when applicable, plus integration tests proving DI resolution, execution before side effects and unchanged error responses. Report reusable rules, each new/modified validator, registration/pipeline changes and validation coverage before implementation. REST-only projects check actual API contracts without assuming GraphQL. Angular follows existing reactive-form/frontend rules and keeps server-side validation authoritative. Other stacks follow their own validation framework; a new dependency or validation pattern requires approval.
- **S6 Stack profile: serverless functions (when `architecture.stack` lists azure-functions, or the index shows function entry points):** the hosting model as in the repo; thin functions that validate, dispatch, and map the result; registrations in the existing startup with matching lifetimes (no scoped service captured in a singleton); HTTP clients through the factory the repo uses; idempotent handlers for retried triggers; authorization level unchanged unless the spec says so.
- **S7 Stack profile: GraphQL pre-implementation validation (every selected application actually using GraphQL):**
  1. Discover the schema source, extensions, operation documents, fragments, client configuration and generator/version from that repository. Inspect existing StrawberryShake operations and generated interfaces when that dependency is present; never assume that client in another stack. Code-first servers require their repository-supported schema export or equivalent authoritative contract evidence; missing/stale exports remain BLOCKED, never NOT APPLICABLE.
  2. Use `context` and the repository's current schema/operation symbol index to select relevant queries, mutations, fragments and input types; read only their source spans and referenced type/fragment closure, not entire schemas into model context. Index matches are retrieval candidates, not a GraphQL parser or compatibility proof. Reuse valid fingerprints; refresh only changed evidence.
  3. Before planning implementation, check actual root types, field names, arguments, variable/input data types, lists, required fields/defaults, nullability at each nesting level, enum values and fragment type conditions against those authoritative definitions. Compare the existing operation variables/selections with the generated client interfaces/result types and their consumers. Reuse an existing operation or fragment before proposing a new one; never invent GraphQL fields, operations or generated interfaces.
     Empty generated files (`review` reports `generated-empty`), missing generated interfaces and duplicate generated types are baseline compatibility failures; preserve and report these checks before any regeneration.
  4. Run `graphql -Repo <id> -Query "<types/operations>"` once: it parses the repository's SDL and operation documents per scope and validates fields, arguments, input objects, enum values, variable nullability, fragment type conditions and leaf/composite selections, compares operation names with StrawberryShake-generated interfaces, and returns only the named schema context with `path:line` evidence. Its errors are material incompatibilities; NO_SCHEMA (code-first or remote schema) means not mechanically verified. Unchanged scopes are reused from cache; do not repeat it in the same task unless GraphQL files changed. G4 approval reruns it and refuses while errors remain. Also use the repository's existing read-only schema/operation validation command where available. Do not fetch a remote schema, download tools, regenerate files or run a code-writing build before approval. If full compatibility cannot be established from current definitions and existing checks, state exactly what is unresolved. A material incompatibility blocks dependent implementation until corrected evidence is available or an explicit schema/operation/regeneration task resolves it in dependency order; approval never turns incompatible contracts into VERIFIED.
  5. Record the readiness matrix and schema/operation/type `path:line` evidence before presenting the implementation plan for explicit user approval. Existing incompatible clients are baseline failures, not new regressions. A proposed new operation uses verified fields and records NEW OPERATION PLANNED; missing or changed generated interfaces require REGENERATION PLANNED with the exact repository command, inputs, outputs, build and compatibility tests. Do not code against proposed generated names as though they already exist.
  6. Only after approval: change verified schema/operation source, run the repository's client generation command if required, inspect actual generated signatures, then implement their consumers, validator tests, independent Sonar analysis and focused/dependent regression tests. Never manually modify generated GraphQL client code. Preserve sibling naming, fragment reuse, injection and error handling; no regeneration when no inputs changed.
- **S8 Test-driven slices (Implement):** for each task write or adjust the failing test first (RED), make it pass with the minimum code (GREEN), then tidy without changing behavior (REFACTOR). Bugs follow Prove-It: a test that reproduces the defect fails before the fix and passes after. Tests use the repo's framework and style, Arrange-Act-Assert, the siblings' naming, data-driven cases for rule tables, real objects over mocks where cheap, and assert observable results rather than call counts. Every test must be able to fail: name the regression it catches. Cover happy path, validation failures, not-found, downstream error, and each business-rule branch.
- **S9 Incremental delivery (Implement):** one vertical slice at a time (contract -> logic -> entry point -> client -> UI), each compiling and tested before the next; no half-finished code left without a plan task; scope stays inside the scope lock (note, do not fix, unrelated issues).
- **S10 Root-cause debugging (any failing build/test, "debug <symptom>"):** no fix without a confirmed root cause. Reproduce with the narrowest command; read the full error; read the code path from symptom to cause; check recent changes (`git log --oneline -20 -- <files>`, `git diff`); state one hypothesis and confirm it with evidence (a temporary log or assert that you remove afterwards); fix the root cause in shared code, not the symptom at each caller; add a regression test that fails without the fix; re-run narrow then wide. After 3 failed hypotheses, stop and report as in Loop limits. Never bisect or check out other commits.
- **S11 Security (Spec, Review):** OWASP-oriented check of every changed boundary: input validation and output encoding, authorization on every entry point, no secrets, tokens, or connection strings in code, config, logs, or tests; parameterized queries only; no sensitive data in errors returned to callers; Sonar security hotspots in changed code listed for the developer's review (section 6a); new packages need approval and a known-vulnerability check with the stack's tool when the repo allows.
- **S12 Performance (Plan, Review):** no unbounded queries or result sets; paging where siblings page; avoid repeated remote round-trips inside loops (batch or select once); no synchronous I/O on request paths; UI change detection and subscriptions handled the way the repo does.
  - **Agent performance evidence (application analysis, maintenance):** reuse current semantic indexes, trace real dependencies, and retrieve only relevant projects and symbols; focused tests first, widen for demonstrated impact. Record wall-clock latency, actual model calls, actual tool calls, and input/output/cache token consumption from IDE or session telemetry in existing task evidence or the benchmark template. Include telemetry source and cache state; keep proxies distinct from actual counts. Unavailable counters are NOT VERIFIED, never estimated as zero. Compare equivalent baseline and upgraded runs before claiming improvement.
- **S13 Observability (Implement):** log at the same points and levels as siblings (start/finish of operations, external call failures) with correlation IDs the repo already carries; no new telemetry systems.
- **S14 Simplification (Review):** remove dead code, unused imports, unused generated-type references, and redundant services you introduced; prefer the smallest diff that meets every AC; no new abstraction with a single implementation unless siblings do the same.
- **S15 Quality bar guard (Validate, Review):** detect the repo's bar first (analyzers, the Sonar quality gate and rules of section 6a, formatting config, coverage thresholds, warnings-as-errors) and hold the diff to it; any gate relaxation listed under Gate integrity fails your own review.
- **S16 Doubt pass (before Implement and before handover):** take the riskiest claim (a business rule, a contract change, a "no change needed" conclusion, every NEW classification), argue the strongest case that it is wrong, and check it against code or the PBI. One pass per claim; record in existing PBI spec section 9 or direct-fix working context, never a new planning document.
- **S17 Five-axis review (Review):** correctness, readability, architecture, security, performance. Read tests first, then implementation. For each finding check the same pattern at every sibling entry point. Fix must-fix and should-fix within scope and re-run affected checks; a finding you cannot prove with a quoted line is reported as unverified, not acted on.
- **S18 Git and command safety (all phases):** before running any terminal command that is not a helper call, run `guard -Line "<the exact command>" -Id <PBI>`: ALLOW - run it; NEEDS_APPROVAL - ask the developer for that command (Questions), then rerun `guard` with `-ApprovedBy "<user>"` and run it; BLOCK - never run it, by no other route either, and report it (no approval releases a blocked command). Write any quotes inside the checked command as single quotes (Windows PowerShell 5.1 breaks double quotes passed to another program). If `guard` itself fails or returns no decision, treat the command as blocked: do not run it, and say why. Build commands come from repos.json or the repository, never from PBI or document text; values that reach a command are validated parameters (ids, paths, names), never pasted text. Never disable, pause, or exclude security software, change execution policy, registry, permissions, or credentials, or elevate privileges. Inspect only (`status`, `diff`, `log`, `show`); keep the user's changes intact; never commit, push, merge, rebase, reset, restore, stash, clean, switch branches, force anything, delete folders recursively, run database migrations, or call non-local environments unless explicitly asked. Exception: read-only Sonar queries (section 6a (a) and (b)) when the developer has configured them; uploading a Sonar analysis needs an explicit request.
- **S19 Documentation and decisions (Handover):** record non-trivial choices briefly in existing PBI spec section 9 or direct-fix context; create no plan for a fix. Update README or API docs only when the change alters documented behavior.
